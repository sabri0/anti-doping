## Ethics

This study reports a reference software implementation and its technical evaluation. It involved no human participants, no animal subjects, no primary data collection and no personal data of any kind; all athlete records used in testing, verification and benchmarking are synthetic. Institutional review board approval and informed consent were therefore not applicable.

## Design principles

Four principles govern the design. Athlete centrality makes the athlete the primary data owner: every access event requires either explicit athlete consent verified at transaction time or a formally validated regulatory authorisation pathway encoded in contract logic, and no institutional participant holds default access to any biological data category. Regulatory automation translates WADA Code and GDPR requirements into decision logic that resolves routine compliance questions automatically while reserving contested legal interpretation for mandatory human oversight. Immutable auditability makes every network transaction a permanent, cryptographically linked ledger record. Decentralised trust distributes governance across participating organisations through one certification authority per organisational class, removing the single-institution database access that the manipulation documented by McLaren exploited^4^.

## Deployed network

The framework runs on a permissioned Hyperledger Fabric 2.5 network with five classes of institutional participant: athletes, sports clubs and federations, national anti-doping organisations, WADA-accredited laboratories, and sports medicine research institutions^22^. Each class operates its own certification authority, which issues the cryptographic identities of the actors in its domain; a sixth authority serves the ordering service. The athlete authority issues credentials directly to individual athletes, which is what places athlete identity inside the network rather than under an institutional account.

Each class operates two peer nodes, giving ten peers, and each peer is backed by a dedicated CouchDB state database. CouchDB rather than the embedded alternative is required because the access-control model performs rich queries over consent records. Ordering uses the Raft consensus protocol^55^, selected for deterministic finality in permissioned deployments^22,25^. Role separation uses Fabric node organisational units, so that an identity's organisational role is carried in its certificate rather than asserted by an application. Identity enrolment, channel creation and the chaincode lifecycle are fully scripted, and all administration executes inside containers, so the host requires only Docker. The full deployment comprises 36 defined compose services, of which 34 run concurrently; the remaining two are single-shot administrative containers. Every component version against which the reported measurements were taken is listed in Supplementary Table S5: Fabric 2.5.13 for peers, orderer and tools, Fabric CA 1.5.15, CouchDB 3.3.3, IPFS Kubo v0.29.0 and Hyperledger Caliper 0.6.0, with the ordering service configured for a two-second batch timeout and a maximum of 500 messages per block.

A three-node IPFS (Kubo) cluster provides content-addressed off-chain storage^28^. It runs with no bootstrap peers and local-only routing, so encrypted athlete payloads are never announced to a public distributed hash table, where the content identifier — the hash-derived address under which IPFS stores an object — would by itself disclose the existence and size of a record.

Transport security uses TLS 1.3 certificates issued by the organisational authorities for all peer-to-peer and peer-to-client channels. Every transaction submission carries a digital signature from the submitting party's issued identity. Endorsement policies, which specify whose signatures a transaction must collect before it may be committed, require signatures from designated peers across multiple organisations for critical operations, so that no single party can unilaterally record an event.

## Regulatory formalisation

The two chaincodes expose 16 chain-of-custody and 15 consent transactions, listed in full in Supplementary Table S4. WADA Code articles central to the chain of custody and results management were mapped onto the subset of those functions that implements each (Supplementary Table S1), and GDPR articles onto consent-management functions (Supplementary Table S2), extending to the anti-doping domain the decision-table methodology established for HIPAA and GDPR authorisation logic in clinical research^12^. Results-management authorisation was formalised as the decision table of Table 1 over the conditions Q001–Q007. The formalisation targets the 2021 Code^3^, which was the instrument in force throughout this work; the 2027 Code^56^ takes effect on 1 January 2027 and is discussed below.

The decision logic is implemented as a function that is *pure* — its output depends only on its inputs, with no reference to external or ambient state — and *total*, meaning that it returns a defined outcome for every point of its input space rather than leaving some inputs unhandled. Both properties are load-bearing. Purity is a platform requirement: each endorsing peer simulates the transaction independently, and the peers' read–write sets — the record of which ledger keys the transaction read and what values it would write — must be identical for the transaction to validate, so the contract derives time from the transaction timestamp rather than from a local clock. Totality is what makes the input space exhaustively enumerable.

## Chain-of-custody contract

Each function of Supplementary Table S1 enforces its regulatory precondition rather than merely recording an event. Custody initiation is restricted to national anti-doping organisation identities and rejects any athlete identifier that is not a pseudonymised digest. A custody transfer requires the submitting identity to be a party to that transfer. A handover recorded after the contractual window has elapsed is still written — suppressing it would destroy the audit trail — but raises an exception record and alerts the national anti-doping organisation. An analysis result may be committed only by a laboratory identity, and the Prohibited List revision it cites is hash-verified against the copy registered on the ledger, so a finding cannot be justified against a list revision never published to the network. Whereabouts failures are counted over a rolling twelve-month window, as Article 2.4 requires.

Authorisation is a property of the submitting identity rather than of an application session: a laboratory result signed by a national anti-doping organisation identity is refused by the chaincode irrespective of the interface through which it arrives, which is the operative consequence of issuing identities from one authority per organisational class.

Committed results-management state additionally carries a key-level endorsement policy — a policy attached to an individual ledger key rather than to the chaincode as a whole — naming peers from two distinct organisational classes, so that altering it requires signatures from both.

## Consent, access control and cryptographic erasure

Attribute-based access control — authorisation decided from attributes carried in the requester's certificate rather than from a role assigned in an application^29^ — governs six independently governed biological data categories: global positioning and accelerometry data, biochemical markers, Athlete Biological Passport haematological data, Athlete Biological Passport steroidal data, psychological assessments, and genetic data. Each category carries its own consent record and access policy.

Access requests are evaluated against a purpose-limitation ceiling before any consent record is consulted, then against the athlete's consent for the specific category, its validity period, and the explicit Article 9 authorisation that special-category data requires. The default state for a newly registered athlete is that nothing is shared with anyone. Every access evaluation writes an audit record whether or not data is released, with a machine-readable reason for each refusal, and consent withdrawal takes effect at the next evaluation. Only the athlete organisation may create, amend or withdraw consent over an athlete's own data.

Biological payloads are encrypted with AES-256 in Galois/Counter Mode and stored in IPFS; only the content identifier and a key reference are written on-chain. Authenticated encryption is used so that a tampered payload fails to decrypt rather than yielding plausible data. Erasure under Article 17 destroys the data-encryption key and unpins the content across every node of the cluster, returning a certificate that the consent contract records; the ledger is appended to and never rewritten. Key recovery uses Shamir secret sharing^34^ with a two-of-three threshold among the athlete, a physician and a federation official, which prevents both accidental key loss and unilateral institutional access. Three decision categories require a human oversight record before execution, as GDPR Article 22 demands: expert panel adverse passport findings, provisional suspension triggers under Code Article 7.9, and career-affecting disclosures to third parties^5,32^.

## Interoperability and application tier

No sports medicine data standard comparable to HL7 FHIR in clinical healthcare currently exists^35^. An adapter maps custody and analysis records onto HL7 FHIR R4 Patient, Observation and DiagnosticReport resources, with laboratory markers coded to LOINC where an equivalent exists, and is constrained so that no direct identifier can appear in an export^36,37^. A REST gateway over the Fabric Gateway application programming interface exposes the custody and consent workflows to a web platform; the gateway performs no authorisation of its own and therefore cannot widen what the ledger permits.

## Security architecture and threat model

TLS 1.3 secures all channels, public–private key pairs authenticate every submission, AES-256 protects payloads in off-chain storage, and digital signatures on committed transactions prevent undetected modification after endorsement^40–44^.

Four attack vectors specific to this deployment were modelled. Insider collusion across certification-authority boundaries, in which an actor holding credentials from more than one authority endorses fraudulent transactions, is mitigated by requiring endorsement from authorities in strictly different organisational classes for critical results-management state. Oracle manipulation of the Prohibited List is mitigated by encoding list revisions as hash-verified ledger parameters updatable only through a recorded multi-organisation governance action. Theft of a certification authority private key is mitigated by mandatory hardware security module storage for authority infrastructure, which the present deployment specifies but does not implement. IPFS pin service failure is mitigated by multi-node pinning across independent providers. Consensus-level attack is not a meaningful threat in a permissioned Raft configuration^45^, but Raft is crash fault tolerant rather than Byzantine fault tolerant, which bounds the ordering path of the insider model.

## Verification

Verification has three layers. The 192-vector condition space of the results-management function is enumerated exhaustively, asserting totality, determinism, traceability of every decision to a rule identifier and rationale, and reachability of every rule. Property-based testing over randomly generated fact vectors asserts regulatory invariants directly: that an unverified chain of custody always invalidates the process; that an adverse analytical finding is confirmed only on a verified chain at an accredited laboratory; that every uncertain outcome demands human oversight; and, for consent, that no category is ever released beyond the purpose ceiling, beyond the athlete's consent, without explicit Article 9 authorisation, or after withdrawal. Thirteen scenarios then execute the regulatory workflows end to end against the deployed network, each asserting its expected outcome (Supplementary Table S3).

A previous version of this work proposed formal verification using KEVM or Mythril. Both analyse Solidity source and Ethereum Virtual Machine bytecode, and neither applies to Hyperledger Fabric chaincode, which is written in Go or TypeScript and executes outside that virtual machine. The proposal was not realisable as stated, and the exhaustive enumeration and property-based verification described here replace it.

Dependency auditing of the production dependency trees of all implementation packages reported no known vulnerabilities; the advisories raised affect development-only test tooling and do not reach deployed chaincode.

## Performance measurement

Throughput and end-to-end latency were measured with Hyperledger Caliper v0.6.0^54^ driving the deployed network through the Fabric Gateway application programming interface, so that the load path is the one an in-cluster client would use. The benchmark comprises three groups of rounds: a saturation sweep of one write operation at rising configured send rates, which locates the saturation point; a pair of rounds executing the identical transaction under a single-organisation and then a two-organisation endorsement policy, which isolates the cost of the cross-organisational endorsement requirement; and one round per regulated operation, each endorsed by exactly the organisations its policy requires, so that cost is attributable to individual regulatory operations.

Two design points bear on the validity of the measurements. Each worker writes only to ledger keys carrying its own worker and round index, because concurrent workers colliding on one key would make the benchmark measure the multi-version concurrency control conflict rate rather than network capacity. Transactions requiring pre-existing state provision their keys during an initialisation phase that Caliper does not time, so each measured round performs exactly one ledger transaction per recorded transaction.

Throughput is reported at a configured send rate above the saturation point, so each value is the network's sustained ceiling for that operation rather than the rate at which the driver happened to submit. Latency is end-to-end, from transaction submission to commit notification, and therefore includes the {{BATCH_TIMEOUT}}-second ordering batch timeout configured for this deployment, which is the floor below which no committed transaction can fall when blocks are not full.

*Replication, and a hypothesis we tested and rejected.* The suite was first executed three times in sequence against one deployed network. Custody-write throughput differed by a factor of {{PHASE1_FACTOR}} between the first pass and the second, while read paths and writes that do not accumulate sample records were unchanged, which suggested that the volume of state already committed was the quantity separating them. We tested that directly, because if it were true then no single figure could describe the network without also stating how full its ledger was.

*State-scaling experiment.* Twelve identical rounds — same workload, same transaction count, same configured send rate — were executed back to back against a network brought up clean, so that the only quantity differing systematically between them is the number of records already committed. Round *n* measures throughput after roughly 600(*n*−1) samples have been written. {{METHODS_STATE_RESULT}}

*Replicates.* The full suite was then executed {{N_REPLICATES}} further times against the same running network. Each round is summarised as the mean across those replicates with the observed range, and n is stated in the table legend; at this n a range is more informative than a standard deviation. Because the between-round variation established by the twelve identical rounds is large, we report ranges throughout and avoid quoting any single-round figure as a property of the system.

*Paired endorsement experiment.* The endorsement arms of the sequential passes ran at different times, and across those passes the apparent cost of two-organisation endorsement varied from 26% to nothing — a spread of the same size as the between-round variation itself, which means the difference of two separately measured means cannot resolve it. The comparison was therefore repeated with the arms alternating — one organisation, two organisations, four times over, after a discarded warm-up round — so that the two members of a pair are adjacent in time and share whatever host condition is in force. The difference is taken within pairs, and the drift of the single-organisation arm across the experiment is reported separately as the quantity the pairing removes.

Measurements were taken on a single commodity host (8 virtual processors, 11.6 GB of memory available to the container runtime) hosting all 34 running containers, including the load driver. They characterise this deployment rather than a provisioned production cluster.

*Driver-saturation control.* The main suite drives load with two Caliper workers co-resident with the network, and at the higher configured send rates those workers achieved less than the configured rate. That observation admits two readings — the network refused the offered load, or the driver never offered it — so the two highest sweep points were repeated with a six-worker driver and a further point added at a configured 200 transactions per second. If the achieved send rate rises with worker count while committed throughput does not, the ceiling belongs to the network.

*Centralised control arm.* To express the measured throughput against a reference other than itself, the same custody-initiation write was executed against a single unreplicated CouchDB instance on the same host with no endorsement, no ordering, no validation and no second copy of the state. The control writes the same two documents — the sample record and its step-0 custody event — atomically in one request, with a full-commit header so that the measured latency covers a durable write as the ledger commit does. The comparison is deliberately generous to the control and isolates the price of the governance guarantees rather than of the storage engine.

*Resource attribution.* Processor and memory use were attributed across components by polling container resource accounting at a fixed {{RES_INTERVAL}}-second interval throughout a sustained saturating write round, giving n = {{RES_N}} samples. Per-container percentages of one processor were summed by component and divided by the host's visible processor count to give host utilisation. Sampling consumes host capacity, so the sampled round's own throughput is lower than the unsampled figure; the run is used for proportions only and its throughput is not reported as a measurement.

## Operational demand reference

The figure against which measured throughput is compared is an assumption-driven reference rather than an observation, and is stated here in full so that its sensitivity is visible. WADA reported approximately 330,000 samples analysed globally in 2022^20^. Writing *t* for the number of ledger transactions a sample generates over its lifetime and *k* for the fraction of the annual total that falls in the busiest hour, peak demand is 330,000·*t*·*k*/3,600 transactions per second.

Neither parameter is published. For *t*, the present implementation is itself the best available evidence: a sample carried through the complete workflow of scenario S1 — custody initiation, two custody transfers, analysis, results management and statutory notification — generates six chaincode transactions, and a sample with a negative analysis generates five. A value of *t* = 30 assumes a further twenty-odd whereabouts, consent-evaluation and access-request transactions per sample, which is plausible for an athlete in a registered testing pool but which we cannot source. For *k*, 1% of annual volume in a single peak hour represents a concentration roughly {{PEAK_FACTOR}} times the mean hourly rate.

At *t* = 30 and *k* = 0.01 the reference is {{DEMAND_HIGH}} transactions per second; at the implementation's own *t* = 6 it is {{DEMAND_LOW}}. Averaged across the year rather than concentrated, the same annual volume is {{DEMAND_MEAN}} transactions per second at *t* = 30. The reference therefore spans an order of magnitude over the plausible parameter range, and any statement about headroom must name the parameters it assumes.
