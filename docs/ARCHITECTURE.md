# Architecture (release 2.0)

Described through the views of the 1+5 architectural views model for
blockchain and information-system integration (Górski, *Symmetry* 2021).

## Use case view

Fourteen executable regulatory workflows, `driver/scenarios.js`
(Supplementary Table S3): AAF confirmed (S1); invalidation on an unaccepted
dispatch (S2), late receipt (S13) and seal mismatch (S14); pending and
unverified accreditation (S3, S4); whereabouts violation (S5); passport alert
(S6); the insider (S7); Article 22 oversight (S8); purpose limitation (S9);
withdrawal (S10); off-chain storage, revocation, recovery and erasure (S11);
confidentiality before and after notice (S12).

## Business process view

Collection → athlete acknowledgement → dispatch (NADO) → receipt (laboratory)
→ analysis → results management → notice → oversight → provisional suspension
or amendment. Consent: grant → request → decision → key release → withdrawal
or revocation → erasure with Article 17(2) notice.

## Logical view

Fig. 3a. `CustodyContract` (`chaincode/custody`) and `ConsentContract`
(`chaincode/consent`), each delegating adjudication to a pure module —
`resultsDecision` (Table 1) and `abac` (six categories) — with no ledger
access. Records:

| Where | Records | Held by |
| --- | --- | --- |
| public world state | sample, custody dispatch and receipt, athlete acknowledgement, custody exceptions, Prohibited List revisions | every peer |
| `resultsCollection` | analysis, decision, amendments, oversight, passport evaluation, whereabouts failures and per-athlete summary, notification | NADO, laboratory |
| `noticeCollection` | notice of an asserted violation, status reports | NADO, laboratory, athlete, federation |
| `consentCollection` | consent, access decisions, payload pointers, recipient lists, erasure records | athlete organisation |

Non-members hold the hashes of private records only.

## Development view

| Path | Contents |
| --- | --- |
| `chaincode/custody`, `chaincode/consent` | contracts, unit, enumeration and property tests |
| `offchain` | encryption, IPFS, weighted Shamir recovery, revocation, erasure, keyed pseudonyms |
| `network` | channel configuration (Raft and SmartBFT profiles), collection definitions, tools image |
| `scripts` | network lifecycle, deployment, evaluation, analysis and figure generation |
| `driver` | load driver, scenarios, insider comparison, tamper-evident-log baseline |
| `gateway`, `web`, `fhir-adapter` | application tier |
| `docs` | formalisation log, threat model, measurement protocol, measurement output |

## Integration view

REST gateway over the Fabric Gateway interface (`gateway`), naming the
endorsing organisations each transaction requires; HL7 FHIR R4 adapter
(`fhir-adapter`); private IPFS cluster for ciphertext; athlete key service.

## Deployment view

Fig. 2. Five organisations, each with a Fabric CA 1.5.15 and two Fabric 3.1.5
peers (CouchDB or LevelDB); four ordering nodes run by the athlete,
federation, NADO and laboratory organisations (etcdraft or SmartBFT); contracts
as external services; three Kubo nodes. Generated by
`scripts/gen-compose.py`; channel by `scripts/create-channel.sh`; contracts by
`scripts/deploy-chaincode.sh`, which defines `custody` (any two organisations),
`custodyor` (any one; endorsement-cost measurement only) and `consent`.
