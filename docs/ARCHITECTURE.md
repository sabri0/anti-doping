# Architecture

How the manuscript's specification maps onto running software. Every claim in
this document corresponds to code or configuration in this repository.

## 1. Network topology

The compose file stands up exactly the participants named in §3.2 of the
manuscript. The 1:1 correspondence is deliberate: it is what makes the prototype
a validation of the paper rather than a generic Fabric demonstration.

```
                       ┌───────────────────────────┐
                       │  orderer.antidoping.org   │  Raft, BatchTimeout 2s
                       └─────────────┬─────────────┘
                                     │
   ┌──────────┬──────────┬───────────┼───────────┬──────────┐
   │          │          │           │           │          │
 Athlete  Federation    NADO    Laboratory   Research      (each: 1 CA,
   │          │          │           │           │          2 peers,
 peer0/1   peer0/1    peer0/1     peer0/1    peer0/1        2 CouchDB)
   │          │          │           │           │
   └──────────┴──────────┴─────┬─────┴───────────┘
                               │
                    channel: antidopingchannel
                    chaincode: custody, consent
                               │
                    ┌──────────┴──────────┐
                    │ ipfs0  ipfs1  ipfs2 │  private cluster, no public DHT
                    └─────────────────────┘
```

Ports are allocated by organization index: CA `7054 + 1000i`, peer *n* of
organization *i* at `(7+i)000 + 51 + 10n`. The compose file is generated by
[scripts/gen-compose.py](../scripts/gen-compose.py) because 36 services differing
only by name and offset are a transcription-error hazard when written by hand.

## 2. Identity and the multi-CA structure

Each organizational class runs its own Fabric CA. Enrollment
([scripts/registerEnroll.sh](../scripts/registerEnroll.sh)) issues, per
organization: a CA administrator, two peer identities, an organization
administrator and an end user, with NodeOU role separation so that
client / peer / admin roles derive from the certificate's OU field.

Authorization in this framework is a property of the **submitting identity**,
not of an application session. `recordSampleAnalysisResult()` refuses any
identity whose MSP is not `LabMSP`, no matter which API route reached it. The
REST gateway therefore cannot widen what the ledger permits; it is a protocol
adapter and nothing more.

## 3. Endorsement: two layers

This is the most consequential design decision in the implementation, and it
departs from a literal reading of the plan.

**Chaincode-level policy** is `OR` over the five organizational classes. A
blanket `AND('NADOMSP.peer','LabMSP.peer')` would have been simpler, but it is
wrong: it would force laboratory endorsement on sample *collection*, an event
the laboratory has no knowledge of and no business attesting to.

**State-based endorsement** supplies the actual §4.1 mitigation. When the
chaincode writes a custody transfer or a results-management record, it binds
that specific key to a policy requiring peers from two distinct organizational
classes:

```ts
const ep = new KeyEndorsementPolicy();
ep.addOrgs('PEER', 'NADOMSP', 'LabMSP');
await ctx.stub.setStateValidationParameter(key, ep.getPolicy());
```

The result is a live, testable property rather than an assertion. Step 7 of
[scripts/e2e-demo.sh](../scripts/e2e-demo.sh) re-runs results management with
NADO endorsement alone and asserts that the network rejects it with
`ENDORSEMENT_POLICY_FAILURE`. "Insider collusion across CA boundaries is
mitigated" becomes something the test suite fails on if it stops being true.

## 5. The Table 2 decision engine

`decideResultsAction(facts)` is pure, total and deterministic over Q001–Q007. It
reads no ledger state, no clock and no randomness — `triggerResultsManagement`
assembles the fact vector and hands it over.

Purity buys exhaustive verification. The condition space is
`2 × 3 × 2 × 2 × 2 × 2 × 2 = 192` vectors, and the test suite enumerates every
one, asserting totality, determinism, well-formedness and rule reachability.
This is complete coverage of the regulatory logic, not sampling.

Determinism is also a hard requirement of the platform: every endorsing peer
simulates the transaction independently and must produce an identical read-write
set. This is why the chaincode reads time from `getTxTimestamp()` rather than the
local clock — wall-clock time would break endorsement outright.

## 6. Off-chain storage and erasure

Biological payloads never reach the ledger. The flow is: AES-256-GCM encrypt →
add ciphertext to every IPFS node → write `{cid, keyRef}` on-chain.

GCM rather than CBC, so ciphertext integrity is authenticated: a tampered
payload fails to decrypt instead of yielding plausible garbage.

The IPFS cluster runs with **no bootstrap peers and local-only routing**
([network/ipfs/init](../network/ipfs/init)). Athlete ciphertext must never be
announced to a public DHT — the CID alone would leak the existence and size of a
record. This also means the client writes bytes to each node directly rather
than pinning-by-fetch, which additionally makes storage deterministic instead of
dependent on network propagation.

Erasure destroys the key and unpins across every node, returning a certificate
that the consent chaincode records. The ledger is appended to, never rewritten —
that is what makes the scheme compatible with an append-only log.

The `KeyVault` holds the sole copy of each key and never hands the buffer out;
`exportForSharing()` returns a copy solely for producing Shamir shares. An
earlier design returned the live buffer, which meant destroying a key silently
corrupted any copy the caller still held.

## 7. Deployment

Chaincode runs as **chaincode-as-a-service**: the contract is a container the
peer connects to over gRPC, rather than something the peer builds and launches.
The artefact deployed is byte-identical to the one the unit tests exercised, and
deployment does not depend on the peer's build environment.

[scripts/deploy-chaincode.sh](../scripts/deploy-chaincode.sh) is idempotent: it
reads the committed sequence number and advances it, so redeploying an amended
contract is a single command.

## 8. Known deviations from the plan

- **Endorsement policy** — state-based endorsement per key instead of a blanket
  chaincode-level `AND`, for the reason in §3 above.
- **Formal verification** — the plan (following the manuscript) mentioned KEVM
  and Mythril. Both target Solidity/EVM bytecode and cannot analyse Fabric
  chaincode. Replaced with exhaustive condition-space enumeration and
  property-based testing. See [THREAT-MODEL.md](THREAT-MODEL.md).
- **Scale** — measured at 5 organizations on one host. 15- and 30-organization
  runs are not reported because they were not performed; nothing is extrapolated
  and presented as measurement.
